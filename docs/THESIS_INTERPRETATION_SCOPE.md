# 论文机制假说模块：范围与审计合同

当前工程验收见 [工程验证方案](ENGINEERING_VALIDATION.md)（2026-10-13）：
六个开发案例与软件/输入扰动验证，无独立双人机制评阅要求。来源审核与以下声明边界仍保留。

## 1. 模块定位

InterpreterPLATO 在论文中应被描述为“可审计的、规则驱动的 post-hoc 生物学机制假说
生成模块”。它把 PLATO 药物靶点、细胞系表达、PPI、通路和疾病基因集整合为候选机制，
并保存从输入证据到结论的追踪信息。

允许的核心表述是：

> 在给定数据版本、规则和阈值下，系统生成了与观察到或预测的药物协同相容、且可追溯
> 到具体靶点、网络路径和通路证据的生物学机制假说。

## 2. 不应作出的声明

本模块单独运行时不能声称：

- 找到了真实作用机制或完成了实验验证；
- 证明了药物组合在患者中的临床疗效；
- 输出分数是靶点正确率、机制真实性概率或实验成功概率；
- 解释了上游协同模型“为什么”给出某一预测；
- PLATO 目标、网络边或通路关系均为因果关系。

`predicted_synergy` 默认只是被记录并用于上下文呈现。只有接入独立定义的模型扰动或消融
协议，并报告其覆盖率、方向一致性和限制后，才可以讨论“与模型行为的一致性”；即便如此，
也不等于模型因果解释。

## 3. 运行模式

| `run_mode` | 用途 | 可进入论文主结果 |
| --- | --- | --- |
| `research_hypothesis` | 使用经审计的真实输入生成论文候选机制假说 | 可，但必须同时满足纳入标准并保留限制语句 |
| `demo` | 演示接口、数据结构和流程 | 不可 |
| `test` | 自动化测试和合成 fixture | 不可 |

当前合同下所有结果均为 `formal_result_eligible=false`。该字段的目的不是评价假说质量，
而是阻止研究性输出被误当作已验证或生产级结论。测试夹具还必须显式声明
`generated_from_test_fixture=true`。

## 4. 输入证据门禁

一对药物只有在下列审计条件通过时，才允许进入机制假说生成：

- 两种药物均有单独归档的 PLATO 响应；
- 查询结构、release、cache schema 和 parser schema 均可验证；
- 原始响应 SHA-256 与独立可信 allowlist 匹配；
- 至少保留一个可靠、明确人源、蛋白类靶点；
- PPI、表达、通路和疾病上下文文件通过锁文件及 SHA-256 校验。

production schema allowlist 当前为空，因此真实 PLATO 导入仍会 fail closed。测试进程可以
临时批准合成 schema 以验证程序，但这类结果必须保持 `run_mode=test`，不能用作研究证据。

## 5. 每个结果的最低审计字段

结果 schema 5.4 同时声明 research contract 1.0 与 statistical contract 1.1。
每个输出至少包含：

- 运行模式、测试夹具标志、声明边界和不具备正式结论资格的原因；
- Git commit（若可得）、工作树状态和实际运行 Python 源码快照哈希；
- 有效配置哈希、随机种子和随机化预算；
- Python、平台和关键依赖版本；
- runtime manifest、数据 artifact 哈希清单；
- 两种药物各自的 PLATO schema、结构绑定和原始响应哈希；
- 靶点排序、机制规则、可信度公式及 PLATO parser 的策略版本；
- 实际进入网络/富集统计的完整靶点集合、网络方法版本、实际接受/拒绝随机化计数及原因；
- 单对支持与批量支持的区别，以及批量分析的完整计划检验家族身份与不可评估状态；
- 排除自身哈希字段后的完整 canonical JSON SHA-256；
- 写盘 JSON 的精确字节 SHA-256 sidecar。

代码快照哈希记录的是实际运行文件内容，所以工作树未提交时仍可识别具体实现；Git dirty
状态用于提示该结果不是仅由某个 commit 唯一决定。

当前网络方法是 `weighted_fixed_disease_closest_v3_mapped_universe`：基于 PPI 边置信度的加权距离、
原始覆盖率达标后对 PPI 内靶点与疾病模块交集计算最近距离均值、与观测靶点不相交的度匹配随机集合。它不是严格的
Cheng 方法复现；可交换性、零模型尾概率和 BH 依赖条件尚未通过独立校准。
完整定义见[统计方法与推断边界](STATISTICAL_METHODS.md)，不能沿用参考文献的验证结论。

## 6. 论文纳入与报告建议

论文主结果中的每个案例至少应同时保存：

1. 原始 PLATO 归档及其来源审核记录；
2. 上下文数据 lock/manifest；
3. `explanation.json` 与 `explanation.json.sha256`；
4. 代码 commit、代码快照哈希和有效配置哈希；
5. 主要机制假说、支持证据、反证/敏感性结果和限制；
6. 如果使用上游模型分数，模型版本、输入样本标识与预测输出哈希；
7. 对规则阈值、基因集和可信度权重的敏感性分析。

建议把结果写为“支持/相容于某机制的证据强度”，不要把未校准的
`mechanism_confidence` 或 `evidence_credibility_score` 写成概率。人工挑选案例时应预先定义
纳入规则，并同时报告失败、证据不足或机制不稳定的组合，以降低选择性报告风险。

网络统计和通路富集使用上下文 top-k 筛选前的完整合格 PLATO 靶点集。top-k 仍可改变展示、
探索性规则和主要假说；但统计输入没有变化时，网络结果恒定是实现的预期行为，不构成独立
网络稳健性证据。解释器中的靶点/模块/路径删除属于敏感性分析，不是生物学因果干预，
也不能替代上游模型的真实重算。

论文评测的纳入漏斗、独立留出、盲评、相加/拮抗对照和资源消融见
[拟议验证协议](VALIDATION_PROTOCOL.md)。该协议状态仍是 `proposed_not_executed`；
回归测试通过不代表已完成独立机制评测。历史 5.2 及更早结果须按 5.3 从原始输入重跑，
不得只修改版本字段或追认旧的支持状态。

## 7. 后续升级条件

若要超出“可审计机制假说”定位，至少需要独立完成：外部数据集校准、阈值和权重冻结、
盲法案例验证、消融/扰动协议、实验验证以及版本化统计分析计划。任何升级都应创建新的
research contract 版本，不能通过修改单个布尔字段追认旧结果。
