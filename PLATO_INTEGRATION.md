# PLATO r37 Integration Boundary

InterpreterPLATO does not call an unpublished PLATO HTTP API and does not
scrape or batch-query the web page. The preferred boundary is one user-triggered
query per molecule on the PLATO platform. The response can be downloaded
manually, or captured by the local single-query helper that submits exactly one
PLATO target-fishing form request and archives the raw JSON plus audit metadata.

`PLATO-only` means the drug target source is PLATO only. It does not mean this
program has an independent target-prediction model, a public API grant, or
batch-query permission; PLATO remains the external platform.

## Single-Query Command

Official website review on 2026-07-16:

- visible navigation links: home, prediction, data, about us, release, and a getting-started PDF;
- no visible Terms of use, Conditions of use, FAQ, Help, or API page link was found in that navigation;
- `robots.txt` on the host returned 404;
- the prediction page exposes a plain `POST` form with `smiles`, `tipoout`, `tipopred`, and `invia`;
- the home/navigation text states "Batch prediction available", but InterpreterPLATO intentionally does not use batch mode.

```powershell
python InterpreterPLATO/scripts/query_plato_once.py `
  --drug-name "Compound-A" `
  --smiles "exact SMILES submitted to PLATO" `
  --release r37 `
  --print-report
```

This sends one `POST` request to the official PLATO target-fishing form
endpoint with `tipoout=json` and `tipopred=mussel`. It rejects non-PLATO
endpoints, performs no loops and no concurrent requests, saves the raw response
bytes, writes a metadata sidecar, records SHA-256, and imports the response with
`query_binding_status=plato_single_query_post_verified`.

This verifies local query binding for the captured response. It is not a PLATO
API contract, a license grant, or cryptographic provider authentication.

## Pair-Level Workflow

The explanation unit is one drug pair. For low-frequency debugging, use the
pair-level helper:

```powershell
python InterpreterPLATO/scripts/query_pair_and_explain.py `
  --drug1 "Drug-A" `
  --drug2 "Drug-B" `
  --cell-line A549 `
  --disease-label pan_cancer_tier1
```

It performs:

1. local exact-name SMILES resolution, unless explicit SMILES are supplied;
2. one PLATO target-fishing JSON form request for drug 1;
3. an optional delay, default 3 seconds;
4. one PLATO target-fishing JSON form request for drug 2;
5. run-scoped raw JSON, sidecar, SHA-256, cache, and manifest archival;
6. strict PLATO-only pair explanation.

Use `--resolve-only` to test local name-to-SMILES resolution without contacting
PLATO. Ambiguous names fail closed and require explicit SMILES.

The two same-run raw response hashes are passed to the interpreter as the
runtime allowlist and recorded as
`trusted_export_sha256_source=same_run_single_query_capture`. For stronger
external audit, freeze those SHA-256 values in an independent manifest and run
the interpreter again with that allowlist.

## ChEMBL r37 Target-ID Translation

PLATO r37 target-fishing JSON returns `chemblId` for targets. Cancer-context
resources in this project are HGNC-normalized, so InterpreterPLATO uses ChEMBL
r37 only as an identifier translation layer:

```text
PLATO target_chembl_id -> ChEMBL r37 target/component -> HGNC 2026-04-01 symbol
```

This does not add targets. Target candidacy still comes only from PLATO. The
mapping output is hash-pinned in the production context and is generated by:

```powershell
python InterpreterPLATO/scripts/build_chembl_target_mapping.py
```

Only unique single-component targets are directly mapped to one HGNC symbol in
the current interpreter. Multi-component complexes/families are retained in the
audit output but are not collapsed into a single gene.

## Manual Archive Command

```powershell
python InterpreterPLATO/scripts/import_plato_result.py `
  --drug-name "Compound-A" `
  --smiles "exact SMILES submitted to PLATO" `
  --result "C:/path/plato-result.json" `
  --release r37 `
  --attest-downloaded-from-plato `
  --print-report
```

The importer first checks that the file exists and is strict UTF-8 JSON. It
then stores a cache schema v3 envelope under
`InterpreterPLATO/data/processed/plato_cache` by default.

`--attest-downloaded-from-plato` means only: "the user says this file was
downloaded from PLATO." It does not prove source, authenticate PLATO, verify
the query molecule, verify the release, or verify field semantics. Without the
flag, the file can still be archived but is marked as unattested.

## Cache And Production Gates

Current cache schema is `3`. A cache entry stores:

- immutable raw response bytes and their SHA-256;
- normalized payload hash;
- normalized target snapshot hash;
- query structure identity;
- parser report;
- audit metadata hash.

Loading the cache recomputes these values. Legacy v1/v2 cache entries are
archive-only and cannot enter a formal v5 result.

Production scoring also requires a controlled, real, desensitized r37 response
fixture. That fixture establishes the release-specific adapter and verifies
field shapes and semantics. This workspace now archives a Gemcitabine PLATO r37
target-fishing JSON response under `data/raw/plato/r37/golden_fixture/`, and
the parser recognizes its `chemblId / nome / score / validato / simili` schema.

This fixture verifies the machine-readable target-fishing schema only. The raw
JSON response does not contain an explicit query SMILES field, so a formal
explanation still requires query-structure binding plus independent raw export
SHA-256 allowlist entries for each drug. A generic alias parser recognizing
target-like records, a payload claiming `r37`, or a user attestation cannot
substitute for those gates.

This document intentionally does not invent r37 provider fields, method fields,
score semantics, or reliability labels. After a real fixture is obtained, record
source/license details, review it independently, and then freeze the accepted
schema fingerprint in code and tests.

## Per-Drug Strict Conditions

Each drug must:

- provide the exact SMILES submitted to PLATO;
- have an RDKit-validated canonical SMILES and InChIKey;
- hit current cache schema v3;
- bind the payload query structure to the submitted structure;
- report the expected release from the payload;
- pass fixture, raw blob, hash, parser output, and audit metadata checks;
- keep only reliable explicit-human protein target records;
- match an independent allowlist entry for the raw PLATO export SHA-256.

Any failure fails closed. The interpreter does not fall back to local targets,
SQLite target databases, or caller-supplied targets.

Formal output declares:

- `result_schema_version=5.1`
- `credibility.formula_version=evidence_credibility_v4_verified_plato_only`

This score describes evidence completeness and auditability. It is not a
probability that the target prediction is correct. Old schema 3/4/5.0, formula
v1/v2/v3, and user-attested-only cache entries must not be mixed with v5.1 results.
